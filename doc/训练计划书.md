## 一、整体架构

### 1.1 代码组织方案：共享工具模块 + 独立训练脚本

采用 **1 个共享工具模块 + 5 个独立训练脚本** 的结构，理由如下：

| 方案 | 优缺点 |
|------|--------|
| 单一大脚本 | 代码冗长，难以并行调试单个模型，一次出错全停 |
| 5 个完全独立脚本 | 大量重复代码（数据加载、分割、评估、保存），维护成本高 |
| **共享工具模块 + 5 个训练脚本** | 数据加载/分割/评估只写一次，每个模型脚本约80-120行，可独立运行 |

### 1.2 目录结构

```
code/train/
├── __init__.py               # 包声明
├── config.py                 # 全局配置（路径、随机种子、超参数默认值）
├── data_loader.py            # 数据加载与用户级划分
├── preprocessing.py          # 预处理（缺失值、标准化、类别编码）
├── evaluation.py             # 统一评估函数（计算所有指标并保存）
├── model_io.py               # 模型保存/加载、预测结果导出
├── train_logistic_regression.py
├── train_decision_tree.py
├── train_random_forest.py
├── train_xgboost.py
└── train_lightgbm.py
```

### 1.3 模块职责划分

| 模块 | 职责 | 对外接口 |
|------|------|----------|
| `config.py` | 所有路径、随机种子、模型保存目录 | `DATA_PATH`, `RANDOM_SEED`, `MODEL_DIR` 等常量 |
| `data_loader.py` | 从 CSV 加载数据，用户级 train/val/test 划分 | `load_and_split()` 返回 (train_data, val_data, test_data)；`extract_xy()` 从中分离 X/y/ids |

| `model_io.py` | 保存模型 (joblib / .pkl)，保存预测结果 (CSV) | `save_model()`, `save_predictions()` |
| 5 个 `train_*.py` | 各自负责一种模型的训练、调参（可手工微调）、调用评估和保存 | 每个脚本独立可运行，产出模型文件和预测 CSV |

## 二、数据加载与划分策略

### 2.1 高效加载

- 使用 `pandas.read_csv()` 分块读取或直接读取（211 MB，在典型 8GB+ 内存机器上 OK）
- 加载后立即分离 `user_id`、`product_id`（标识列）和 `reordered`（目标列）
- 特征矩阵 X：17 列；目标向量 y：`reordered` 列

```python
IDENTIFIER_COLS = ['user_id', 'product_id']
TARGET_COL = 'reordered'
FEATURE_COLS = [c for c in df.columns if c not in IDENTIFIER_COLS + [TARGET_COL]]
```

### 2.2 用户级划分（User-Level Split）—— 核心防泄漏机制

**问题**：如果按行随机划分，同一用户的多个样本可能分布在训练和测试集中，造成数据泄露（模型在训练时已经"见过"该用户的模式）。

**方案**：
1. 获取全体唯一 `user_id` 列表（131,209 个）
2. 按 **60/20/20** 比例随机划分用户：
   - Train users: ~78,725 个用户（约 78.4 万行）
   - Val users: ~26,242 个用户
   - Test users: ~26,242 个用户
3. 根据划分的 user_id 集筛选对应的数据行

**实现细节**：
```python
def user_level_split(df, random_state=42):
    # df 包含 'user_id' 列
    unique_users = df['user_id'].unique()
    np.random.seed(random_state)
    np.random.shuffle(unique_users)
    
    n = len(unique_users)
    n_train = int(n * 0.6)
    n_val = int(n * 0.2)
    
    train_users = unique_users[:n_train]
    val_users = unique_users[n_train:n_train + n_val]
    test_users = unique_users[n_train + n_val:]
    
    train_mask = df['user_id'].isin(train_users)
    val_mask = df['user_id'].isin(val_users)
    test_mask = df['user_id'].isin(test_users)
    
    return train_mask, val_mask, test_mask
```

**验证**：确保 train/val/test 的 user_id 集合互不相交（没有重复用户）。

### 2.3 划分后校验

- 验证三个集合的 user_id 交集为空
- 打印各集合的行数、正样本比例，确保与整体分布一致（约 59.9% reordered=1）

## 三、预处理策略

### 3.1 各特征的处理方式

| 特征分组 | 特征列 | 处理 | 说明 |
|----------|--------|------|------|
| 计数特征 | user_total_orders, user_total_products, user_unique_products, product_total_orders, product_unique_users, up_order_count, up_last_order, up_orders_since_last | 保持原值 | 已是 int32，无需缩放（树模型可直接处理） |
| 比率特征 | user_reorder_ratio, product_reorder_rate, department_reorder_rate, up_order_rate | 保持原值 | 已是 [0,1] 区间 |
| 均值特征 | user_avg_days_between_orders, user_avg_cart_size, product_avg_cart_position, up_order_span | 保持原值（树模型）/ StandardScaler（LR） | LR 需要标准化 |
| 类别特征 | department_id (int: 1-21) | One-Hot 编码（21 类）或保持原值（树模型） | LR 必须 One-Hot 以消除序数假设 |

### 3.2 Logistic Regression 专用预处理

Logistic Regression 对尺度敏感，需要以下预处理流水线：

```python
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler, OneHotEncoder
from sklearn.compose import ColumnTransformer

# 数值特征标准化
numeric_features = 除 department_id 外的所有 16 个特征

# 类别特征 One-Hot
department_id 列

preprocessor = ColumnTransformer([
    ('numeric', StandardScaler(), numeric_cols),
    ('categorical', OneHotEncoder(sparse_output=True), ['department_id'])
])
```

- 使用 `sparse_output=True` 以节省内存
- LogisticRegression 传入 `solver='saga'` 以支持稀疏输入 + L1 正则化

### 3.3 树模型（Decision Tree / Random Forest / XGBoost / LightGBM）预处理

- **不缩放**：树模型基于分裂阈值，对特征尺度不敏感
- `department_id`：保持 int 原值即可。XGBoost/LightGBM 可直接传入 `categorical_feature=['department_id']` 参数，Decision Tree / Random Forest 原值即可
- 无需 One-Hot：树模型能正确处理编码后的整数值

### 3.4 类别不平衡处理

- 正样本比例约 59.9%，负样本 40.1%，不平衡不严重（比例约 1.49:1）
- **不需要** SMOTE 或重采样
- LightGBM / XGBoost 可使用 `scale_pos_weight` 参数（值 ≈ 负样本数/正样本数 ≈ 0.67），轻微调节
- 评估时关注 Recall、F1、PR-AUC 以确保不平衡下的模型质量

## 四、各模型训练方案

> **随机种子**：全部使用 `random_state=42`。  
> **硬件假设**：8GB+ 内存，CPU 训练（无 GPU 假设，但 XGBoost/LightGBM 可 GPU 加速）。

### 4.1 Logistic Regression

**定位**：线性基线模型。

| 维度 | 设定 |
|------|------|
| 预处理 | StandardScaler + OneHot (dept_id) |
| 模型 | `sklearn.linear_model.LogisticRegression` |
| solver | `saga`（支持 L1/L2/elasticnet，支持稀疏输入） |
| penalty | `l2`（默认），可候选 `l1` 做对比 |
| C | 默认 1.0，可在 val 上微调 [0.1, 1.0, 10] |
| max_iter | 1000（确保收敛） |
| class_weight | `balanced`（自动处理类别不平衡） |
| 内存关注 | One-Hot 后维数增加至 16 + 21 = 37 列，可控 |

**训练流程**：
1. 拟合 ColumnTransformer（标准化 + OneHot）
2. 转换训练集
3. 训练 LR 模型
4. 验证集评估
5. 保存模型和预测结果

### 4.2 Decision Tree

**定位**：单棵树基线，主要用于对比集成模型效果提升。

| 维度 | 设定 |
|------|------|
| 模型 | `sklearn.tree.DecisionTreeClassifier` |
| 预处理 | 无需缩放/One-Hot |
| max_depth | 控制过拟合，候选 [8, 12, 15, None] |
| min_samples_leaf | 1000（约 78 万行下，防止末端节点过小） |
| min_samples_split | 5000 |
| class_weight | `balanced` |
| 内存关注 | 单棵树内存占用极小 |

**训练流程**：
1. 直接使用原始特征训练
2. 在验证集上选择最优 max_depth
3. 用选定参数重新在 train+val 上训练，在 test 上评估

### 4.3 Random Forest

**定位**：Bagging 集成基线，兼顾效果与稳定性。

| 维度 | 设定 |
|------|------|
| 模型 | `sklearn.ensemble.RandomForestClassifier` |
| 预处理 | 无需缩放/One-Hot |
| n_estimators | 100（兼顾速度与效果） |
| max_depth | 12（限制以避免内存爆炸和过拟合） |
| min_samples_leaf | 1000 |
| min_samples_split | 5000 |
| n_jobs | -1（全核并行） |
| class_weight | `balanced` |
| bootstrap | True（默认） |
| 内存关注 | 100 棵树 × 78 万行 = 较大，需监测内存。如不够，降 n_estimators=50 |

**内存优化**：
- 使用 `max_depth` 限制树深以减少模型体积
- 保存时使用 `joblib.dump(model, f, compress=3)` 压缩

### 4.4 XGBoost

**定位**：Boosting 基线1，通常效果最好之一。

| 维度 | 设定 |
|------|------|
| 模型 | `xgboost.XGBClassifier` |
| 预处理 | 无需缩放；dept_id 可传 `enable_categorical=True` |
| n_estimators | 300（早停决定实际迭代数） |
| max_depth | 6 |
| learning_rate | 0.1 |
| subsample | 0.8 |
| colsample_bytree | 0.8 |
| scale_pos_weight | 约 0.67（neg/pos） |
| tree_method | `hist`（基于直方图的快速算法，CPU 友好） |
| eval_metric | `logloss` |
| early_stopping_rounds | 30（验证集上无提升即停） |
| 内存关注 | hist 方法内存效率高；`eval_set` 需传入验证数据 |

**训练流程**：
1. 将 `department_id` 标记为 categorical
2. 使用 train 训练，val 做早停
3. 取 `best_iteration` 模型做 test 评估

### 4.5 LightGBM

**定位**：Boosting 基线2，速度最快，处理类别特征原生支持好。

| 维度 | 设定 |
|------|------|
| 模型 | `lightgbm.LGBMClassifier` |
| 预处理 | 无需缩放；categorical_feature=['department_id'] |
| n_estimators | 300（早停） |
| max_depth | 7 |
| num_leaves | 31 |
| learning_rate | 0.1 |
| subsample | 0.8 |
| colsample_bytree | 0.8 |
| scale_pos_weight | 约 0.67 |

| 内存关注 | LightGBM 内存效率最高，直方图算法 |

## 五、评估框架

### 5.1 统一评估函数

所有模型共享同一个评估函数 `evaluate_model()`，位于 `evaluation.py`：

```python
def evaluate_model(y_true, y_pred, y_proba, model_name):
    """
    计算所有指标并返回 dict，同时打印格式化表格
    返回: dict with keys:
        accuracy, precision, recall, f1,
        roc_auc, pr_auc, log_loss
    """
    from sklearn.metrics import (
        accuracy_score, precision_score, recall_score,
        f1_score, roc_auc_score, average_precision_score,
        log_loss
    )
    
    metrics = {
        'model': model_name,
        'accuracy': accuracy_score(y_true, y_pred),
        'precision': precision_score(y_true, y_pred),
        'recall': recall_score(y_true, y_pred),
        'f1': f1_score(y_true, y_pred),
        'roc_auc': roc_auc_score(y_true, y_proba),
        'pr_auc': average_precision_score(y_true, y_proba),
        'log_loss': log_loss(y_true, y_proba),
    }
    return metrics
```

### 5.2 指标说明

| 指标 | 说明 | 主要/次要 |
|------|------|-----------|
| **Recall** | 真实再次购买中预测正确的比例 | **主要** — 漏掉复购的代价高 |
| **F1-score** | Precision 与 Recall 的调和平均 | **主要** — 综合衡量 |
| **ROC-AUC** | 排序能力 | **主要** — 考察模型区分能力 |
| **PR-AUC** | 正类排序能力（对不平衡敏感） | **主要** — 补充 ROC-AUC |
| Accuracy | 总体正确率 | 次要 |
| Precision | 预测为正类中真正的比例 | 次要 |
| LogLoss | 概率校准质量 | 次要 |

### 5.3 结果汇总

在每个训练脚本结束后，将指标追加到一个汇总 CSV 文件 `output/metrics_summary.csv`（所有模型一行一行追加），便于后续比对。

## 七、内存管理策略

### 7.1 数据加载阶段

- 全部加载（211 MB 在内存中约 300-400 MB）
- pandas 自动使用 float32/int32 精度的特征，已是优化过的
- **不**使用 Dask 或 Vaex（对单机 138 万行 overkill）

### 7.2 训练阶段

| 模型 | 内存风险 | 对策 |
|------|----------|------|
| Logistic Regression | 低 | One-Hot 后 37 列，无问题 |
| Decision Tree | 低 | 单棵树内存极小 |
| Random Forest | **中等** | max_depth=12 限制深度；n_jobs=-1 仅影响 CPU 不影响内存；joblib 压缩保存 |
| XGBoost | 低 | tree_method='hist' 使用直方图算法 |
| LightGBM | 低 | 原生直方图算法，内存效率最高 |

### 7.3 内存监控

- 在每个训练脚本中，训练前后打印 `memory_usage()` 便于排查
- 训练完成后显式删除中间变量，避免内存残留：
  ```python

## 八、实验流程（每个训练脚本的通用骨架）

```
1. 导入模块（config, data_loader, preprocessing, evaluation, model_io）

8. 调用 model_io 保存模型和预测 CSV

## 九、超参数调优策略

### 9.1 调优范围

考虑到全量数据 138 万行，GridSearchCV 时间复杂度不可接受。采用以下策略：

| 策略 | 说明 |
|------|------|
| **手工微调** | 基于经验设定初始值，手动在 val 上对比 2-3 个候选值 |
| 不采样调优 | 不降低数据量，直接全量训练 |
| 早停机制 | XGBoost/LightGBM 自带 early stopping |

### 9.2 各模型调优项

| 模型 | 调优参数 | 候选值 |

| Random Forest | n_estimators, max_depth | [50, 100] × [8, 12] |
| XGBoost | max_depth, learning_rate | [4, 6, 8] × [0.05, 0.1] |

## 十三、潜在风险与应对

| 风险 | 概率 | 应对 |
|------|------|------|
| 内存不足（Random Forest 100棵树） | 中 | 降 n_estimators=50，或 max_depth=8 |
| LogisticRegression 不收敛 | 低 | max_iter=2000, solver='saga' |
| XGBoost/LightGBM 版本不兼容 | 低 | 脚本中打印版本号以便排查 |
| 训练时间过长 | 中 | 按顺序先跑快的，后台跑慢的；RF 降低树数量 |
| 数据路径不一致 | 低 | 统一通过 config.py 管理路径 |
| department_id 缺失值 | 极低 | feature_engineering.py 已 fillna(0)，无缺失 |
